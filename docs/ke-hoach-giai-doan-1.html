2. Kiến trúc tổng thể

Agent luôn là bên chủ động gọi lên (pull). Server không cần mở kết nối vào máy cửa hàng, nên không bị ảnh hưởng bởi NAT/firewall, và máy offline cũng không làm server phải chờ.

3. Fingerprint và khóa máy

Theo yêu cầu, mọi lần gửi dữ liệu đều kèm fingerprint. Cần phân biệt rõ hai vai trò:

Fingerprint: "máy này là máy nào"

Mã băm từ đặc điểm phần cứng và hệ điều hành. Server dùng nó để nhận ra máy, và để phát hiện máy bị thay linh kiện hoặc bị clone.

Khóa riêng của máy: "đúng là máy đó gửi"

Cặp khóa Ed25519 sinh ngay trên máy lúc đăng ký. Khóa riêng không bao giờ rời máy. Mọi gói tin được ký bằng khóa này.

Vì sao fingerprint thôi là chưa đủ: serial, MAC hay machine-id đều đọc được và sao chép được. Ai biết fingerprint của một máy (ví dụ từ log, ảnh chụp màn hình, hoặc lúc sửa máy) có thể gửi dữ liệu giả dưới tên máy đó. Fingerprint dùng để định danh, còn khóa riêng dùng để xác thực.

Thành phần fingerprint

fingerprint = SHA-256(
    /etc/machine-id
  + serial mainboard   (dmidecode -s baseboard-serial-number)
  + serial hệ thống    (dmidecode -s system-serial-number)
  + MAC card mạng chính
)

Server lưu từng thành phần riêng, không chỉ lưu mã băm cuối. Lý do: máy RAID 1 có thể thay ổ, card mạng có thể thay. Quy tắc gợi ý:

Thay đổiXử lý
1 thành phần đổi (thay ổ, thay card mạng)Chấp nhận, cập nhật fingerprint, ghi sự kiện "thay linh kiện"
Từ 2 thành phần đổi trở lênTạm khóa máy, cảnh báo admin (nghi clone hoặc cài lại)
Cùng fingerprint xuất hiện từ 2 khóa khác nhauCảnh báo mức cao: nghi clone image có sẵn agent đã đăng ký

Kết hợp với IP WAN do server tự quan sát

Agent không khai IP WAN. Máy sau router/firewall chỉ thấy IP LAN; nếu để agent tự điền IP WAN thì kẻ sửa source có thể điền IP của cửa hàng thật. Thay vào đó, server lấy IP nguồn trực tiếp từ kết nối TCP (giá trị này không giả được nếu không ngồi trong mạng cửa hàng), rồi tự gộp với fingerprint:

Agent gửi:    fingerprint (+ chữ ký bằng khóa riêng)
Server thấy:  IP WAN thật của kết nối

site_key = SHA-256(fingerprint + IP WAN quan sát được)
→ so với danh sách site_key đã duyệt của máy này

Mỗi máy có thể có nhiều site_key hợp lệ (line chính, line dự phòng). Server vẫn lưu riêng fingerprint và IP để biết lệch ở phần nào:

FingerprintIP WANKết luậnXử lý
KhớpKhớpBình thườngNhận dữ liệu
KhớpLạĐổi line, failover 4G, nhà mạng đổi IP, hoặc khóa bị dùng ở nơi khácNhận, gắn cờ, cảnh báo; admin duyệt để thêm site_key. Cửa hàng IP tĩnh có thể bật chế độ nghiêm: từ chối
Lệch 1 thành phầnKhớpThay ổ hoặc card mạng tại cửa hàngNhận, cập nhật hồ sơ, ghi sự kiện "thay linh kiện"
Lệch từ 2 thành phầnBất kỳNghi clone hoặc cài lại máyTạm khóa máy, cảnh báo
Lưu ý hạ tầng: nếu cửa hàng kết nối về trung tâm qua VPN/MPLS, server sẽ thấy IP nội bộ của tunnel thay vì IP WAN. Khi đó dùng IP tunnel hoặc ID tunnel trên router/firewall làm "điểm cố định" thay cho IP WAN, cơ chế giữ nguyên. Nếu đi qua load balancer, phải cấu hình để Ingest nhận được IP gốc (PROXY protocol), không phải IP của load balancer.
Liên quan việc ghost máy: image Ubuntu dùng để ghost không được chứa agent đã đăng ký, và phải xóa /etc/machine-id trước khi đóng image. Nếu không, hàng loạt máy sẽ có cùng machine-id và cùng khóa.

4. Đăng ký lần đầu và duyệt máy

Đây là bước máy gửi thông tin ban đầu và chờ admin duyệt. Không dùng bootstrap token: mọi máy đều phải được admin duyệt trên web trước khi gửi được dữ liệu, nên máy lạ chạy source agent chỉ nằm trong hàng chờ.

  1. Kỹ thuật viên
    Đặt hostname đúng quy ước (12345-TN1-PRI, 12345-TN2-SEC, 12345-TN3…), cài gói agent, chạy scs-agent fingerprint để kiểm hostname và lấy mã khóa máy đối chiếu với yêu cầu trên web.
  2. Agent
    Sinh cặp khóa Ed25519 (lưu trong TPM nếu máy có), thu thập fingerprint, mã cửa hàng, hostname, phiên bản Ubuntu.
  3. Agent → Server
    Gửi gói enroll qua TLS: public key, fingerprint và từng thành phần, hostname, phiên bản Ubuntu. Gói được ký bằng khóa riêng vừa sinh.
  4. Server
    Kiểm tra chữ ký, đọc hostname theo quy ước <mã siêu thị>-TN<số>[-PRI|-SEC] và so IP kết nối với IP WAN cố định của siêu thị. Mọi máy đều vào hàng chờ admin duyệt, không tự duyệt; hostname sai quy ước hoặc IP lạ thì gắn cảnh báo để admin xem kỹ.
  5. Admin duyệt
    Server ghi máy vào DB (siêu thị, vị trí TN), gán IP WAN cho siêu thị nếu là máy đầu tiên, ký và trả về chứng chỉ client (hạn 90 ngày). Agent tự kéo bộ rule về sau đó.
  6. Agent
    Lưu device_id và chứng chỉ vào /etc/scs-agent/ (quyền 600, chủ sở hữu root). Từ đây chuyển sang chế độ vận hành thường.

Máy đang chờ duyệt gửi lại gói enroll (cùng khóa) mỗi 5 phút để hỏi trạng thái. Agent gọi server qua IP WAN của server, cổng được chuyển tiếp (port forward) về 6222; chứng chỉ server phải ghi đúng IP đó.

5. Lưu trữ dữ liệu (PostgreSQL + TimescaleDB)

Database là nơi lưu chính, không dùng folder theo máy. Server chỉ nhận và lưu, không gửi yêu cầu nào cho agent (agent tự kéo rule và bản cập nhật); cảnh báo chỉ hiện trên web.

Để dữ liệu chính xác: ràng buộc nằm ngay trong DB nên code có lỗi cũng không ghi được dữ liệu sai — hostname hợp lệ phải đúng quy ước PRI/SEC; mỗi vị trí TN trong siêu thị và mỗi hostname chỉ một máy đang hoạt động; mỗi gói có nonce, gửi lại không bị ghi hai lần; server chỉ trả OK cho agent sau khi đã ghi xong; lưu cả giờ server nhận lẫn giờ máy gửi (đồng hồ máy có thể lệch); trạng thái online/offline tính theo giờ server nhận, không tin máy tự báo.

6. Truyền dữ liệu và mã hóa

Ba lớp bảo vệ cho mỗi gói tin:

LớpCơ chếChống lại
Đường truyềnTLS 1.3, agent chỉ tin CA nội bộ nhúng sẵn (certificate pinning)Nghe lén, giả mạo server
Xác thực máymTLS bằng chứng chỉ riêng từng máyMáy lạ kết nối vào
Nội dungPayload ký Ed25519, kèm fingerprint, timestamp, nonceSửa nội dung, gửi lại gói cũ (replay), giả mạo máy khác

Kiểm tra phía server cho mỗi gói tin

  1. Chứng chỉ mTLS hợp lệ và chưa bị thu hồi.
  2. device_id trong payload khớp với chứng chỉ.
  3. Chữ ký payload đúng với public key đã lưu khi đăng ký.
  4. Fingerprint khớp với hồ sơ (áp dụng quy tắc ở mục 3).
  5. Ghép fingerprint với IP WAN server quan sát được thành site_key, so với danh sách đã duyệt của máy (mục 3).
  6. Timestamp lệch không quá 5 phút, nonce chưa từng xuất hiện trong 10 phút gần nhất.

Sai bất kỳ bước nào: từ chối, ghi audit; nếu lặp lại nhiều lần thì cảnh báo.

Nếu yêu cầu dữ liệu vẫn được mã hóa cả khi đi qua proxy có giải mã TLS, có thể thêm lớp mã hóa payload bằng public key của server (X25519 + ChaCha20-Poly1305). Lớp này tùy chọn, quyết định sau khi khảo sát hạ tầng mạng.

  "fingerprint": "9f2c...e1",

  "body": { ... },
  "sig": "ed25519:..."             // chữ ký trên toàn bộ các trường phía trên

}

8. Mô hình bảo mật khi lộ source

Nguyên tắc: giao thức có thể công khai, an toàn nằm ở khóa riêng từng máy. Source agent không chứa bất kỳ bí mật dùng chung nào.

Người có source agent có thể

  • Đọc hiểu toàn bộ định dạng gói tin
  • Tạo yêu cầu đăng ký, nhưng chỉ nằm ở hàng chờ cho tới khi admin duyệt
  • Nếu có root trên một máy thật: gửi dữ liệu giả dưới tên chính máy đó (giảm thiểu bằng TPM; mang khóa ra ngoài cửa hàng để dùng sẽ bị phát hiện qua IP WAN lạ)

Người có source agent không thể

  • Giả mạo bất kỳ máy nào khác
  • Đưa máy lạ vào hệ thống khi admin chưa duyệt
  • Đọc dữ liệu của máy khác trên đường truyền
  • Đẩy rule giả hoặc bản cập nhật giả xuống agent (không có khóa ký)
  • Gửi lại gói tin cũ (bị chặn bởi nonce và timestamp)

Danh sách bắt buộc

  • Không hardcode API key, mật khẩu hay khóa mã hóa chung trong source.
  • Khóa ký rule và khóa ký bản cập nhật giữ offline hoặc trong HSM, không nằm trên server Ingest.
  • File cấu hình và khóa của agent: quyền 600, chủ sở hữu root.
  • Server giới hạn tần suất theo từng máy và theo từng IP.
  • Có thể obfuscate binary để làm chậm người phân tích, nhưng không coi đó là lớp bảo vệ chính.

10. Rule quét log

Rule được nhóm thành bộ rule và gán theo nhóm máy (loại máy, vùng, cửa hàng). Mỗi bộ có số phiên bản và chữ ký số. Agent chỉ áp dụng bộ rule có chữ ký hợp lệ; nếu sai chữ ký thì giữ bộ cũ và báo lỗi.

rule_set: pos-default
version: 2026.10.27-03
rules:
  - id: SSH-FAIL-01
    source: /var/log/auth.log
    match: 'Failed password for .* from (?P<ip>\S+)'
    severity: medium
    aggregate: { window_s: 300, threshold: 5 }   # 5 lần trong 5 phút mới báo

  - id: USB-ADD-01
    source: journald
    unit: kernel
    match: 'New USB device found'
    severity: low

  - id: RAID-DEGRADED-01
    source: journald
    unit: mdmonitor
    match: 'DegradedArray|Fail'
    severity: critical

  - id: POS-SVC-DOWN-01
    source: journald
    unit: pos.service
    match: 'Failed with result'
    severity: high

Rule giới hạn ở regex và đếm ngưỡng. Agent không chạy lệnh từ rule ở giai đoạn 1, nhờ vậy dù bộ rule có bị can thiệp thì cũng không thực thi được gì trên máy.

11. Cập nhật agent

  1. Đội phát triển build gói .deb và ký bằng khóa phát hành offline.
  2. Đưa lên update repo, gán vòng triển khai: vòng 0 (máy lab), vòng 1 (1%), vòng 2 (10%), vòng 3 (toàn bộ).
  3. Heartbeat của máy thuộc vòng hiện tại nhận thông tin update.
  4. Agent tải gói, kiểm chữ ký, cài bản mới và giữ bản cũ ở /opt/scs-agent/previous/.
  5. Nếu trong 10 phút bản mới không gửi được heartbeat thành công, agent tự quay về bản cũ và báo lỗi.
  6. Tỷ lệ lỗi của vòng dưới 0,5% sau 24 giờ thì mở vòng tiếp theo.

Chạy song song một watchdog rất nhỏ, độc lập với agent, chuyên khởi động lại hoặc rollback agent. Watchdog hiếm khi phải cập nhật.

Rule hoặc bản cập nhật sai chữ kýTừ chối, giữ bản đang chạy, báo cáo ở heartbeat kế tiếp
Đồng hồ máy lệchĐồng bộ NTP; nếu lệch quá 5 phút, server trả giờ chuẩn để agent bù trừ

Giới hạn tài nguyên của agent qua systemd: CPUQuota=10%, MemoryMax=128M, Nice=10, để không ảnh hưởng ứng dụng bán hàng chạy trên máy.

16. Chuẩn bị cho giai đoạn 2

Những quyết định đưa vào ngay từ giai đoạn 1 để sau này mở rộng sang kiểm soát toàn diện mà không phải viết lại:

  • Trường v trong mọi gói tin: server hỗ trợ đồng thời nhiều phiên bản giao thức, nên nâng cấp server và agent không cần đồng loạt.
  • Agent khai báo khả năng (các module hiện có) ở heartbeat; server chỉ gửi yêu cầu agent hỗ trợ.
  • Agent chia module: đăng ký, trạng thái, quét log, cập nhật. Giai đoạn 2 thêm module thực thi lệnh, bật/tắt được từ server.
  • Kênh liên lạc tách khỏi nội dung message: giai đoạn 1 dùng polling HTTPS; giai đoạn 2 có thể chuyển sang kết nối giữ liên tục (MQTT hoặc gRPC stream) để server gửi lệnh tức thì.
  • Lệnh giai đoạn 2 ký bằng khóa riêng, tách khỏi khóa TLS và khóa ký rule, kèm phân quyền, duyệt 2 người cho lệnh nguy hiểm và audit log.

18. Câu hỏi còn mở

  1. Toàn bộ máy có TPM 2.0 không, hay chỉ các dòng máy mới?
  2. Nội dung chi tiết của phần trạng thái trong heartbeat.
  3. Danh sách log cần quét ở giai đoạn 1 (SSH, USB, service POS, RAID, đăng nhập desktop...).
  4. Có proxy giải mã TLS trên đường từ cửa hàng về trung tâm không? Quyết định việc cần thêm lớp mã hóa payload hay không.
  5. Cửa hàng dùng IP WAN tĩnh hay động, có line dự phòng không, và kết nối về trung tâm qua Internet hay VPN/MPLS?
  6. Thời gian lưu trữ log theo yêu cầu nội bộ và theo luật bảo vệ dữ liệu cá nhân.
