1. Phạm vi giai đoạn 1

Agent chỉ quan sát và báo cáo, chưa nhận lệnh điều khiển máy. Server không gửi lệnh: mọi thứ agent cần (cấu hình, bản agent, rule) đều do agent tự kéo về qua heartbeat.

2. Kiến trúc tổng thể

  • Agent luôn là bên chủ động gọi lên (pull). Server không mở kết nối vào máy cửa hàng nên không vướng NAT/firewall, máy offline không làm server phải chờ.
  • Một binary scs-server chạy được từng vai trò riêng (ingest, admin, worker) hoặc tất cả (all, mặc định khi cài bằng menu). Quy mô hiện tại chạy một máy; khi mở rộng thì tách vai trò ra nhiều node mà không phải viết lại.
  • Thư viện giao thức dùng chung (common/) giữa agent và server: định nghĩa gói tin, fingerprint, chữ ký, quy ước hostname.

Agent gọi server bằng địa chỉ nào cũng được

Agent chỉ kiểm chứng chỉ server có do CA riêng của server cấp (và dùng cho server), không so IP hay tên miền trong chứng chỉ. Vì vậy agent ở VLAN khác, gọi qua IP WAN có NAT, hay server đổi IP đều không phải cấp lại chứng chỉ. Không giả được server vì CA này chỉ cấp chứng chỉ server cho scs-server; chứng chỉ của các máy agent chỉ dùng được cho client.

Nhiều địa chỉ, tự chuyển khi mất kết nối

Server giữ danh sách địa chỉ agent được dùng (SCS_AGENT_SERVERS, ví dụ IP LAN, IP WAN, tên miền DDNS), gửi xuống lúc duyệt và ở mỗi heartbeat. Agent lưu lại; địa chỉ đang dùng không kết nối được thì thử ngay địa chỉ kế tiếp. Mặc định triển khai chỉ trong mạng nội bộ; mở cho agent từ Internet về sau bằng menu (thêm IP WAN / tên miền) mà không phải cài lại agent.

4. Fingerprint và khóa máy

Mọi gói tin đều kèm fingerprint. Cần phân biệt rõ hai vai trò:

Fingerprint: "máy này là máy nào"

Mã băm từ đặc điểm phần cứng và hệ điều hành. Server dùng để nhận ra máy, và (sau này) phát hiện máy bị thay linh kiện hoặc bị clone.

Khóa riêng của máy: "đúng là máy đó gửi"

Cặp khóa Ed25519 sinh ngay trên máy lúc cài, lưu ở /etc/scs-agent/key.pem (quyền 600). Khóa riêng không bao giờ rời máy; dùng cho cả chữ ký từng gói tin lẫn chứng chỉ mTLS.

Vì sao fingerprint thôi là chưa đủ: serial, MAC hay machine-id đều đọc được và sao chép được. Fingerprint dùng để định danh, còn khóa riêng dùng để xác thực.

Thành phần fingerprint

fingerprint = SHA-256(
    /etc/machine-id
  + serial mainboard   (/sys/class/dmi/id/board_serial)
  + serial hệ thống    (/sys/class/dmi/id/product_serial)
  + MAC card mạng chính
)

Server lưu từng thành phần riêng, không chỉ mã băm cuối, để sau này xử lý thay linh kiện:

Thay đổiXử lý dự kiếnTrạng thái

Từ 2 thành phần đổi trở lênCảnh báo admin (nghi clone hoặc cài lại)Chưa làm

Mỗi siêu thị một IP cố định do server tự quan sát

Agent không khai IP. Server lấy IP nguồn trực tiếp từ kết nối TCP. Máy đầu tiên được duyệt của một siêu thị đặt IP đó làm IP cố định của siêu thị; máy khác (hoặc lần sau) gửi từ IP khác thì sinh cảnh báo wan_ip_mismatch trên web. Đã làm

Trong mạng nội bộ nhiều lớp (cửa hàng nối về trung tâm qua VPN/MPLS hoặc định tuyến nội bộ), IP server thấy là IP nội bộ của máy hoặc của tunnel, không phải IP WAN; cơ chế giữ nguyên, "IP cố định" khi đó là IP nội bộ. Nếu sau này đặt load balancer phía trước, phải cấu hình để server nhận được IP gốc (PROXY protocol).
Ghost máy: image Ubuntu dùng để ghost không được chứa agent đã đăng ký, và phải xóa /etc/machine-id trước khi đóng image; nếu không, hàng loạt máy sẽ có cùng machine-id và cùng khóa.

5. Đăng ký lần đầu và duyệt máy Đã làm

Không dùng bootstrap token: mọi máy đều phải được admin duyệt trên web trước khi gửi được dữ liệu, nên máy lạ chạy source agent chỉ nằm trong hàng chờ (tối đa 5.000 yêu cầu chờ, giới hạn tần suất theo IP).

  1. Admin
    Đóng gói agent khung trên server (menu mục 11): một file .tar.gz gồm binary, script cài, CA và khóa công khai phát hành của server, địa chỉ server.
  2. Kỹ thuật viên
    Đặt hostname đúng quy ước (12345-TN1-PRI, 12345-TN2-SEC, 12345-TN3…), giải nén gói, chạy sudo bash scs-agent/scripts/install.sh. Script kiểm hostname, đồng hồ NTP, kết nối và chứng chỉ server, cài dịch vụ, in mã khóa máy.
  3. Agent → Server
    Gửi gói enroll qua TLS: khóa công khai, fingerprint và từng thành phần, hostname, phiên bản Ubuntu; gói ký bằng khóa riêng vừa sinh.
  4. Server
    Kiểm giờ (lệch tối đa 5 phút), chữ ký bằng chính khóa trong gói, fingerprint khớp các thành phần, đọc hostname theo quy ước, so IP với IP cố định của siêu thị. Mọi máy vào hàng chờ; hostname sai hoặc IP lạ thì gắn cảnh báo.
  5. Duyệt tự động (tùy chọn)
    Công tắc ở trang Chờ duyệt (mặc định tắt, mức Agent). Bật thì mỗi lần máy hỏi, server duyệt ngay nếu đủ: hostname đúng quy ước; siêu thị đã có thông tin trong dữ liệu đã nạp; máy gửi từ một IP WAN của siêu thị; không trùng hostname / vị trí TN với máy đang hoạt động. Thiếu thì chờ người duyệt, lý do hiện trên thẻ máy. Người duyệt ghi "duyệt tự động", nhật ký ghi kèm IP.
  6. Admin duyệt
    Trang Chờ duyệt: đối chiếu mã khóa, bấm Duyệt (hostname sai quy ước thì nhập mã siêu thị). Server cấp chứng chỉ client làm từ chính khóa của máy (không cần CSR), CN = mã máy, hạn 90 ngày; DB chỉ nhận serial chứng chỉ mới nhất.
  7. Agent
    Hỏi lại 5 phút một lần (±20%), nhận và kiểm chứng chỉ, lưu vào /etc/scs-agent/, chuyển sang gửi heartbeat; từ đây nhận cấu hình và bản agent từ server.

Thu hồi máy trên web: chứng chỉ không còn được nhận; muốn dùng lại phải cài lại agent (khóa mới) và duyệt lại.

6. Agent khung và cập nhật từ server Đã làm

Máy tại điểm bán chỉ cài một lần bản agent khung. Bản khung do root sở hữu (/opt/scs-agent/scs-agent), dịch vụ agent không sửa được. Mọi bản sau do server phát hành, agent tự kéo về; kể cả bản khung cũng được thay bằng bản đã chạy tốt (xem cuối mục). Không đẩy cập nhật xuống hàng nghìn máy, không phải đóng gói hay cài lại.

  1. Server
    Mỗi lần cập nhật server (menu mục 4) build kèm bản agent cùng phiên bản (linux amd64, arm64). Server nhập vào kho, ký bằng khóa phát hành Ed25519 (tách khỏi khóa CA), lưu vào DB.
  2. Admin
    Trang Agent trên web: bấm Phát hành nhóm thử (các máy đánh dấu "nhóm thử" trong chi tiết máy), theo dõi số máy đang chạy từng bản, ổn rồi bấm Phát hành tất cả. Dừng phát hành thì máy giữ bản đang chạy; phát hành lại bản cũ là quay về.
  3. Server phân lượt
    Mọi lần tải (bản agent, bộ rule, chứng chỉ máy mới hòa mạng) phải giữ lượt; chỉ báo update cho máy giữ được lượt tải: tối đa 4 máy cùng lúc (SCS_DOWNLOAD_SLOTS), tổng ≤ 20 Mbit/s (SCS_DOWNLOAD_MBPS); lượt hết hạn sau 15 phút. Máy chưa tới lượt chạy bản cũ, xin lại ở heartbeat sau. Trang Agent có biểu đồ tiến độ và thống kê phiên bản, bộ rule, trạng thái máy.
  4. Agent
    Heartbeat nhận update (phiên bản, kiến trúc, SHA-256, kích thước, chữ ký). Agent tải qua kết nối có chứng chỉ máy, kiểm SHA-256 và chữ ký bằng khóa công khai phát hành (/opt/scs-agent/release.pub, root sở hữu, đóng trong gói cài), lưu vào thư mục trạng thái, rồi tự thoát để systemd khởi động lại.
  5. Bản khung
    Lúc khởi động, kiểm chữ ký lần nữa rồi chuyển sang chạy bản đã tải (exec). Bản mới gửi được heartbeat thì được ghi nhận là chạy tốt.
  6. Tự quay về
    Bản mới chết 3 lần (trong cùng một lần bật máy) mà chưa gửi được heartbeat: bản khung đánh dấu bản đó hỏng, chạy tiếp chính nó, 24 giờ sau mới thử lại. Máy tắt / khởi động lại (đổi boot_id) hay mất mạng không bị tính là lỗi.
Bản khung đóng vai watchdog: nó luôn còn trên máy và là đường lui khi bản cập nhật lỗi.

Thay bản khung từ server

Bản khung thuộc root để tiến trình agent không tự sửa được, nên việc thay nó do một tác vụ chạy bằng root làm (scs-agent-promote.timer, 30 phút một lần, gọi scs-agent promote). Tác vụ này không tin gì trong thư mục trạng thái (nơi agent ghi được) ngoài thứ kiểm được bằng chữ ký.

  1. Điều kiện
    Bản agent mới đã gửi heartbeat tốt trên chính máy đó được 1 giờ.
  2. Tác vụ root
    Đọc file bản đó (không theo symlink), kiểm SHA-256 và chữ ký bằng release.pub của root, chạy thử version, rồi chép vào /opt/scs-agent. Bản khung cũ giữ ở scs-agent.prev.
  3. Xác nhận
    Lần khởi động sau, bản khung mới ghi dấu đã khởi động; gọi được server (hoặc chuyển được sang bản khác) thì ghi dấu chạy tốt, bản cũ được dọn.
  4. Tự quay về
    Đã khởi động mà 30 phút chưa chạy tốt: trả lại bản khung cũ, không dùng bản đó làm bản khung nữa.

Kẻ chiếm được tiến trình agent chỉ ép được máy dùng một bản khác cũng có chữ ký của server (ví dụ bản cũ) làm bản khung, hoặc ép quay về bản khung trước; không cài được bản tự chế. Máy cài bằng gói trước bản này chưa có tác vụ, cần cài lại một lần.

Rủi ro còn lại: file tải về nằm trong thư mục mà user scs-agent ghi được; ai đã chiếm được user này có thể đổi file giữa lúc kiểm chữ ký và lúc chạy. Người đó vốn đã có khóa máy, nên mức tác động thấp. Khóa phát hành hiện nằm trên server (quyền 600); khi lên quy mô lớn nên chuyển sang ký offline.

7. Cấu hình agent đặt trên web Đã làm

Cấu hình nghiệp vụ không đóng vào gói cài. Admin đặt trên trang Agent, theo ba cấp, cấp cụ thể hơn thắng:

máy  >  siêu thị  >  chung

Hiện có: danh sách dịch vụ systemd cần báo trạng thái (ví dụ dịch vụ bán hàng, máy in). Server gửi xuống kèm mã phiên bản cấu hình; agent báo lại mã đang dùng, server chỉ gửi khi khác. Chưa đặt ở cấp nào thì không gửi, agent giữ giá trị trong agent.env. Sau này thêm: bộ rule gán theo nhóm, nhịp gửi log.

Kiểm tra phía server cho mỗi gói tin của máy đã duyệt

  1. Chứng chỉ mTLS do CA ký (lúc bắt tay TLS).
  2. Máy còn trạng thái đã duyệt, serial chứng chỉ đúng serial mới nhất trong DB.
  3. device_id trong payload khớp CN của chứng chỉ.
  4. Chữ ký payload đúng khóa công khai đã lưu khi đăng ký.
  5. Timestamp lệch không quá 5 phút (agent tự bù theo header Date của server).

Sai bước nào cũng từ chối. Agent tự giãn nhịp khi bị từ chối hoặc server bận.

Nếu đường từ cửa hàng về trung tâm có proxy giải mã TLS, có thể thêm lớp mã hóa payload bằng khóa công khai của server (X25519 + ChaCha20-Poly1305). Lớp này tùy chọn, quyết định sau khi khảo sát hạ tầng.

10. Mẫu payload

Gói tin trên đường truyền

{
  "payload": "eyJ2IjoxLCJ0eXBlIjoi...",   // phong bì bên dưới, mã hóa base64
  "sig": "..."                          // Ed25519 trên "scs-agent/v1\n" + payload
}

Phong bì (bên trong payload)

{
  "v": 1,                          // phiên bản giao thức
  "type": "heartbeat",             // enroll | heartbeat | log_batch (sau)
  "device_id": "42",               // trống với gói enroll
  "fingerprint": "9f2c...e1",
  "ts": "2026-10-31T09:00:05Z",
  "nonce": "b6c1f0a9e2...",        // ngẫu nhiên 16 byte
  "agent_version": "v0.3.0",
  "body": { ... }
}

Heartbeat (body)

{
  "uptime_s": 18230,
  "arch": "amd64",                 // server chọn đúng bản agent
  "config_version": "3f9a0c1d",    // cấu hình agent đang dùng
  "rule_set_version": "",
  "log_queue_pending": 0,
  "status": { ... }                // MachineStatus: ổ đĩa, RAM, RAID, NTP, dịch vụ (sẽ gửi ở mốc A2)
}

Phản hồi của server

{
  "ok": true,
  "next_poll_s": 300,                       // server điều chỉnh nhịp gọi
  "server_time": "2026-10-31T09:00:05Z",
  "servers": ["https://192.168.1.10:6222", "https://ten.ddns.net:16222"],
  "config": { "version": "3f9a0c1d", "watch_services": ["pos.service"] },
  "update": { "version": "v0.3.0", "arch": "amd64", "sha256": "...", "size": 7667872, "sig": "..." },
  "rule_set_version": ""                    // khác bản đang chạy thì agent tải rule (sau)
}

config chỉ có khi khác bản agent đang dùng; update chỉ có khi máy cần chạy bản khác.

11. Mô hình bảo mật khi lộ source

Nguyên tắc: giao thức có thể công khai, an toàn nằm ở khóa riêng từng máy và khóa của server. Source agent không chứa bí mật dùng chung nào; gói cài chỉ có chứng chỉ CA và khóa công khai.

Người có source agent có thể

  • Đọc hiểu toàn bộ định dạng gói tin
  • Tạo yêu cầu đăng ký, nhưng chỉ nằm ở hàng chờ cho tới khi admin duyệt
  • Nếu có root trên một máy thật: gửi dữ liệu giả dưới tên chính máy đó (mang khóa đi chỗ khác sẽ bị phát hiện qua IP lạ)

Người có source agent không thể

  • Giả mạo máy khác hoặc giả làm server
  • Đưa máy lạ vào hệ thống khi admin chưa duyệt
  • Đọc dữ liệu của máy khác trên đường truyền
  • Đẩy bản agent giả xuống máy (không có khóa phát hành)
  • Dùng lại chứng chỉ cũ sau khi máy bị thu hồi hoặc đã cấp chứng chỉ mới

Danh sách bắt buộc

  • Không hardcode API key, mật khẩu hay khóa mã hóa chung trong source; mật khẩu chỉ nằm trong file cấu hình quyền 600.
  • Khóa CA và khóa phát hành: quyền 600, user dịch vụ scs; quy mô lớn thì chuyển khóa phát hành và khóa ký rule sang ký offline / HSM.
  • Khóa máy agent: quyền 600, user scs-agent; dịch vụ chạy với systemd hardening, chỉ thêm quyền đọc serial phần cứng.
  • Web quản trị: mã đăng nhập 6 số đổi mỗi phút (đọc trên server bằng scs-login-code), mã Admin = quản trị gốc (mức 0), mã Chỉ xem (mức 7); khóa khi nhập sai nhiều lần, không chạy sau reverse proxy.
  • Tài khoản web quản trị bằng Gmail: đăng ký, xác minh mã qua mail, quản trị gốc duyệt và đặt mức quyền 1–7 (cụm server, rule, agent + bản cập nhật, địa chỉ server, xác nhận sự cố, thông tin agent, chỉ xem; mức trên có quyền mức dưới). Đăng nhập bằng mã gửi về mail, hạn 5 phút, nhập một lần. Gửi mail qua SMTP bắt buộc STARTTLS (SCS_SMTP_*).
  • Giới hạn tần suất và số kết nối theo IP trên cổng agent; giới hạn kích thước body theo từng route.
  • Khóa đăng nhập theo IP / thiết bị: sai mã 5 lần liên tiếp cho một tài khoản → khóa 24 giờ; sai tên / đăng ký sai quá 10 lần trong 24 giờ → khóa 7 ngày; IP siêu thị khóa theo trình duyệt (quá 3 trình duyệt → khóa IP). Mức 1 quản lý tài khoản mức 5–7. Đã làm 19/11/2026
  • Phiên web gắn với IP + trình duyệt lúc đăng nhập (cookie bị lộ đem sang máy khác thì bị thu hồi); quản trị gốc đặt thời gian sống phiên (1 giờ – 15 ngày) và số phiên cùng lúc (1 – 20) cho từng tài khoản; tên đăng ký chỉ chữ số. Đã làm 18/11/2026
  • Chứng chỉ máy tự gia hạn khi còn dưới 30 ngày (cần agent bản mới); sao lưu DB định kỳ 15 ngày; cập nhật server tự kiểm SQL trên PostgreSQL thật trước khi cài. Đã làm 18/11/2026

13. Rule quét log Một phần

Agent và server dùng cùng một khung rule (common/rules): cùng định nghĩa, cùng hàm kiểm tra, cùng bộ máy khớp và đếm ngưỡng. Admin viết bộ rule bằng YAML, server kiểm, chạy thử trên log mẫu rồi ký bằng khóa phát hành (ngữ cảnh ký riêng, không dùng thay được cho chữ ký bản agent); agent kiểm chữ ký và kiểm lại nội dung y như server, sai thì giữ bộ cũ. Cách viết chi tiết: docs/huong-dan-viet-rule.md.

Rule được nhóm thành bộ rule và gán theo nhóm máy (dùng chung cơ chế cấp chung / siêu thị / máy như cấu hình agent). Mỗi bộ có số phiên bản; agent chỉ tải lại khi phiên bản khác bản đang chạy.

name: mau-co-ban
version: '2026.11.10-01'
rules:
  - id: SSH-FAIL-01
    severity: medium
    source: /var/log/auth.log
    match: 'sshd\[\d+\]: Failed password for (?:invalid user )?(?P<user>\S+) from (?P<ip>\S+)'
    aggregate: { window_s: 300, threshold: 5, group_by: ip }   # cùng IP 5 lần / 5 phút mới báo
    cooldown_s: 1800

  - id: RAID-DEGRADED-01
    severity: critical
    source: journald
    unit: mdmonitor.service
    match: '(?:DegradedArray|Fail) event detected on md device (?P<md>/dev/md\S+)'
    tests:
      match: ['DegradedArray event detected on md device /dev/md0']
PhầnTrạng thái

Rule giới hạn ở regex RE2 (chạy tuyến tính, không treo được agent) và đếm ngưỡng, chỉ đọc file trong /var/log hoặc journald. Agent không chạy lệnh từ rule ở giai đoạn 1, nên dù bộ rule bị can thiệp cũng không thực thi được gì trên máy.

18. Chuẩn bị cho giai đoạn 2

  • Trường v trong mọi gói tin: server hỗ trợ nhiều phiên bản giao thức cùng lúc, nâng cấp server và agent không cần đồng loạt.
  • Agent khai báo khả năng (module đang có) ở heartbeat; server chỉ gửi yêu cầu agent hỗ trợ.
  • Agent khung + cập nhật có chữ ký đã sẵn: thêm module mới chỉ là phát hành bản mới, không phải cài lại máy.
  • Kênh liên lạc tách khỏi nội dung: giai đoạn 1 dùng polling HTTPS; giai đoạn 2 có thể chuyển sang kết nối giữ liên tục để gửi lệnh tức thì.
  • Định hướng: agent cho Windows Chưa làm — ưu tiên Windows 10/11 IoT Enterprise LTSC và Windows 10/11 64-bit (Server 2016+ nếu có, bỏ Windows 7/8.1). Dùng lại lõi agent; làm mới: đọc Windows Event Log (khớp theo kênh + Event ID + provider), bật Audit Policy, Windows Service, tự cập nhật kiểu Windows, trạng thái máy qua WMI, MSI, ký mã Authenticode, hostname ≤ 15 ký tự (NetBIOS). Bước đầu: kiểm kê máy Windows tại siêu thị.
  • Lệnh giai đoạn 2 ký bằng khóa riêng, tách khỏi khóa TLS, khóa phát hành và khóa ký rule; kèm phân quyền, duyệt 2 người cho lệnh nguy hiểm và audit.

Sau phần phát triển: kiểm thử bảo mật (giả mạo máy, replay, bản cập nhật giả), pilot 100–200 máy ở 20–30 cửa hàng (tiêu chí: heartbeat thành công trên 99%, agent dùng dưới 5% CPU), rồi mở rộng theo vùng.

Kết quả chạy thật (19/11/2026, khoảng 150 máy): 5–15 heartbeat / phút, CPU máy server 1–5%, RAM scs-server 25–35 MB, DB 13 MB; phân lượt tải đúng 4 lượt, ≤ 20 Mbit/s.

20. Câu hỏi còn mở

  1. Gia hạn chứng chỉ máy (hạn 90 ngày): Đã làm — phải phát hành bản agent có tính năng này cho mọi máy trước khi chứng chỉ đầu tiên hết hạn (agent bản cũ không tự gia hạn).
  2. Danh sách log cần quét ở giai đoạn 1 (SSH, USB, dịch vụ bán hàng, RAID, đăng nhập desktop...).
  3. Có proxy giải mã TLS trên đường từ cửa hàng về trung tâm không? Quyết định việc thêm lớp mã hóa payload.
  4. Khi nào chuyển khóa phát hành sang ký offline (trước pilot hay trước mở rộng)?
  5. Thời gian lưu trữ log theo yêu cầu nội bộ và theo luật bảo vệ dữ liệu cá nhân (đang để 60 ngày).

Đã chốt từ bản nháp đầu

  • Mạng: triển khai trong mạng nội bộ nhiều lớp (VLAN định tuyến qua nhau); agent gọi server bằng IP nội bộ, mở ra Internet về sau nếu cần.
  • TPM: chưa dùng ở giai đoạn 1; khóa máy là file quyền 600.
  • Trạng thái trong heartbeat: đã định nghĩa (ổ đĩa, RAM, swap, tải CPU, RAID phần mềm, đồng bộ NTP, dịch vụ theo dõi).
  • Cập nhật agent: bản mới do server phát hành theo nhóm, không dùng gói .deb; bản khung được thay bằng bản đã chạy tốt, có kiểm chữ ký.
  • Lưu trữ: DB là nơi lưu chính, dữ liệu theo ngày giữ 60 ngày, cảnh báo chỉ hiện trên web.
